# AngelscriptDebugServer 断点判定细节（引擎侧）

> 对应源码：
> - `AngelscriptCode/Private/Debugging/AngelscriptDebugServer.h / .cpp` —— 调试服务器、断点状态机
> - `AngelscriptCode/Private/AngelscriptManager.cpp` —— 回调注册（`AngelscriptLineCallback` / `AngelscriptStackPopCallback`）与 `UpdateLineCallbackState`
> - AngelScript 引擎改造点：`asCContext`（行回调开关）、`asCModule::hasBreakPoints`、`asCScriptFunction::FindNextLineWithCode`、`m_loopDetectionTimer`

## 1. 三类断点，三套完全不同的机制

| 类型 | 实现层 | 判定方式 |
|---|---|---|
| **行断点 / 单步** | AngelScript 虚拟机（软断点） | `LineCallback` 逐行回调中查表比对 |
| **异常断点** | AngelScript 虚拟机 | 脚本抛异常时 `ProcessException` 被动触发 |
| **数据断点** | CPU 硬件（x86 调试寄存器 DR0-DR3） | Windows SEH 向量化异常处理器捕获 `EXCEPTION_SINGLE_STEP` |

## 2. 行回调：一切软断点的入口

### 2.1 回调注册与性能门控

上下文创建时（`AngelscriptManager.cpp:626-627`）注册：

```cpp
Context->SetLineCallback(AngelscriptLineCallback);
Context->SetStackPopCallback(AngelscriptStackPopCallback);   // 数据断点出栈检测用
```

`LineCallback` 每执行一行脚本字节码就会被调用一次，代价很高。因此引擎侧改造了 `asCContext` 增加两级静态开关（`UpdateLineCallbackState`，`AngelscriptManager.cpp:3947-3979`）：

| 开关 | 置位条件 | 效果 |
|---|---|---|
| `CanEverRunLineCallback` | `bIsDebugging` 为真 **或** 存在数据断点 | 该 context **可能**跑行回调；再叠加每模块 `hasBreakPoints` 标志决定实际是否调 |
| `ShouldAlwaysRunLineCallback` | `bBreakNextScriptLine`（即将单步） | 无条件每行都回调（step/pause 需要） |

`asCModule::hasBreakPoints` 是模块级标志：`SetBreakpoint` 时置 true、`ClearBreakpoints`/`ClearAllBreakpoints` 时置 false——**没设断点的模块连行回调的判定都直接跳过**。这三层门控组合起来，调试未启用时行回调几乎零开销。

`AngelscriptLineCallback` 本身还有两道保护：只处理游戏线程（`IsInGameThread()`）、`GAngelscriptLineReentry` 防重入（行回调期间执行的脚本不再触发行回调，如调试监视求值）。

### 2.2 ProcessScriptLine 判定流程（AngelscriptDebugServer.cpp:357-525）

```
LineCallback (per script line, game thread)
  └─ ProcessScriptLine(Context)
       ├─ early out: !bIsDebugging / bIsPaused / engine exit requested
       │
       ├─ [A] data breakpoint follow-up handling (see §4)
       │
       ├─ [B] bBreakNextScriptLine?            (step / pause / data bp)
       │     ├─ bShouldBreak = true
       │     ├─ step-over/step-out guard:
       │     │    ConditionBreakFrame/Function set?
       │     │    if Context->GetFunction(CheckFrame) == ConditionBreakFunction
       │     │       → bShouldBreak = false   (still inside the frame we stepped from)
       │     ├─ generated function guard:
       │     │    asTRAIT_GENERATED_FUNCTION → bShouldBreak = false
       │     │    (auto-generated code has no cursor position to show)
       │     └─ break → bIsPaused = true, reason = "step"
       │
       ├─ [C] else if BreakpointCount > 0
       │     && currentFunction->module->hasBreakPoints
       │     ├─ Line, Section = Context->GetLineNumber(0)
       │     ├─ SectionBreakpoints cache lookup (by section name)
       │     ├─ if ActiveBreakpoints->Lines.Contains(Line)
       │     │    && !(Line == IgnoreBreakLine && Section == IgnoreBreakSection)
       │     │    && ShouldBreakOnActiveSide()
       │     │        → bIsPaused = true, reason = "breakpoint"
       │     └─ update IgnoreBreakLine/Section
       │
       └─ if bIsPaused → PauseExecution(StoppedMessage(reason))
```

细节说明：

- **SectionBreakpoints 缓存**：`Breakpoints` 是 `TMap<模块名, FFileBreakpoints{Module, Lines:TSet<int32>}>`；`SectionBreakpoints` 以脚本的 section 名（源文件名）为 key 做二级缓存，行回调里避免每次查模块表。缓存 miss 时从模块名对应的 store 拷一份引用。
- **`IgnoreBreakLine` / `IgnoreBreakSection`（去抖）**：命中断点暂停时记下 (line, section)，继续执行后**同一行不再停**（防止该行剩余字节码/循环反复触发）；一旦执行到了别的行就复位。
- **`ShouldBreakOnActiveSide()`**：PIE 多端（如多人同步调试）时，通过 `FAngelscriptCodeModule::GetDebugCheckBreakOptions()` 委托结合 `BreakOptions`（异常过滤器集合）决定"只在活跃端"停；无 WorldContext 或委托未绑定时默认停。

## 3. 单步的实现：bBreakNextScriptLine + 条件帧

AngelScript 本身没有 step 语义，全部用"下一行必停 + 帧条件豁免"模拟（`HandleMessage`，`AngelscriptDebugServer.cpp:718-786`）：

| 命令 | `bBreakNextScriptLine` | `ConditionBreakFrame` | `ConditionBreakFunction` |
|---|---|---|---|
| `StepIn` | true | -1 | null（无豁免，任何行都停） |
| `StepOver` | true | `CallstackSize - 1` | 当前函数（栈顶） |
| `StepOut` | true | `CallstackSize - 2` | 第 1 层调用者 |
| `Pause` | true | -1 | null |
| `Continue` | false | 清空 | 清空 |

ProcessScriptLine [B] 的豁免判定：

```cpp
int32 CheckFrame = CallstackSize - ConditionBreakFrame - 1;
if (CheckFrame > 0 && Context->GetFunction(CheckFrame) == ConditionBreakFunction)
    bShouldBreak = false;
```

- **StepOver**：记下当时的栈大小 N 和当前函数。只要"距离栈顶还差 N-1 层的地方仍是那个函数"，说明还没返回出发帧的更外层——即在出发帧内部或其被调函数里，继续跳过；一旦出发帧返回（CheckFrame 变成指向外层），条件不再匹配 → 停。
- **StepOut**：条件设在 `CallstackSize - 2`（出发时的父帧），在当前帧及其兄弟调用中都不停，直到回到父帧才停。

另外 `asTRAIT_GENERATED_FUNCTION` 的函数（脚本热重载/生成的胶水代码）永远不停——没有对应的可显示源码。

## 4. 暂停的本质：游戏线程忙等

```cpp
void PauseExecution(FStoppedMessage* StopMessage)
{
    bIsPaused = true;
    SendMessageToAll(HasStopped, *StopMessage);

    // 关闭该 context 的死循环检测计时，防止长断点触发"脚本超时"误报
    Context->m_loopDetectionTimer = -1.0;

    while (bIsPaused)                        // ← 游戏线程阻塞在此
    {
        ProcessMessages();                   //   轮询 socket 处理 Continue/断点变更/求值
        FPlatformProcess::Sleep(0);          //   让出时间片
    }

    SendMessageToAll(HasContinued, ...);
}
```

暂停 = 游戏线程在回调里自旋。**好处**：暂停期间整个引擎世界状态天然冻结、`asGetActiveContext()` 仍然有效，`RequestVariables` / `RequestEvaluate` 直接在游戏线程上下文中遍历 AngelScript 栈取值，无需暂停时刻的快照。所有停止原因（`breakpoint` / `step` / `pause` / `exception`）都汇聚到这一个函数。

## 5. 行断点的设置流程（HandleMessage: SetBreakpoint）

```
SetBreakpoint(filename, line, id, moduleName)
  ├─ CanonizeFilename()                                路径规范化
  ├─ GetModuleByFilenameOrModuleName()                 定位脚本模块
  ├─ Key = ModuleName（找不到模块则用文件名兜底）
  ├─ FoundModule->hasBreakPoints = true
  ├─ CodeLine 解析：
  │    遍历模块所有 scriptFunctions:
  │      Func->FindNextLineWithCode(WantedLine)        该函数中 ≥ WantedLine 的最近"有字节码"的行
  │      取所有函数中 (LineInFunc - WantedLine) 最小者 → BestLine
  │    找不到：id != -1 时 CodeLine = -1（回告移除）
  ├─ CodeLine 有效 → Active->Lines.Add(CodeLine)（去重），BreakpointCount++
  └─ CodeLine != WantedLine 且 id != -1
       → 回发 SetBreakpoint(原文件名, CodeLine, id)  ← 断点"漂移"到实际代码行
```

要点：

- **断点行校正是"向前吸附"**：`FindNextLineWithCode` 找的是该函数内 ≥ 请求行的最近一行**真实生成字节码**的行（跳过空行/注释/声明），DAP 端收到回告后更新 UI 上的断点位置。
- **断点表是模块键控的**：脚本热重载后模块对象重建，`ReapplyBreakpoints()` 重新按模块名绑定 `Module` 引用并重置 `hasBreakPoints`。
- `BreakpointCount` 全局计数是 [C] 判定的快速短路条件；文件级 `ClearBreakpoints` 只清对应模块的行集。

## 6. 异常断点

AngelScript context 抛异常 → `ProcessException(Context)`（`AngelscriptDebugServer.cpp:332-355`）：

- 若已在暂停中直接返回；先 `ProcessMessages()` 排空消息再判定 `bIsDebugging`；
- `Reason = "exception"`，`Text = Context->GetExceptionString()`；
- 走 `PauseExecution` —— DAP 端把 reason == 'exception' 的 StoppedEvent 呈现为异常暂停，`exceptionInfo` 请求返回缓存的 Text。
- 是否在异常上实际停下由 `BreakOptions`（`setExceptionBreakpoints` 设置的过滤器列表 + 隐式追加的 `break:any`）+ 引擎各处的检查决定。

## 7. 数据断点：x86 调试寄存器（仅 Windows，`WITH_AS_DEBUGSERVER`）

### 7.1 设置（SetDataBreakpoints → UpdateDataBreakpoints）

```
SetDataBreakpoints(breakpoints[])
  └─ DataBreakpoints = breakpoints（id / uint64 地址 / 1|2|4|8 字节 / hitCount / bCppBreakpoint）
  └─ UpdateDataBreakpoints()
       └─ FUpdateDebugRegisterThread（最高优先级临时线程）
            ├─ DuplicateHandle 获得游戏线程真实句柄
            ├─ SuspendThread(游戏线程)                 RAII guard（结束 ResumeThread）
            ├─ GetThreadContext(CONTEXT_DEBUG_REGISTERS)
            ├─ Dr7 &= 0x3F00; Dr7 |= 0x1000            按规范初始化
            ├─ ApplyBreakpointsToThreadContext：
            │    for i in 0..(num breakpoints, ≤4):
            │      Dr[i] = Address                     写入 Dr0~Dr3
            │      Dr7 |= 1 << (i*2)                   Local enable
            │      写条件位 = 01b（仅写触发）
            │      尺寸位：1B=00b 2B=01b 4B=11b 8B=10b（DR7 的 16+i*4 起的 4 bit）
            │      （状态非 Keep 的槽位跳过 = 禁用该寄存器）
            └─ SetThreadContext
```

必须 suspend 线程的原因：调试寄存器属于线程上下文，无法从其他线程直接改写。最多 4 个 = DR0~DR3 的物理限制。

### 7.2 触发（Vectored Exception Handler）

构造 DebugServer 时 `AddVectoredExceptionHandler(0, DebugRegisterExceptionHandler)` 挂上（优先级最高）。硬件断点命中 → CPU 陷入 `EXCEPTION_SINGLE_STEP`：

```
DebugRegisterExceptionHandler(ExceptionInfo)
  ├─ 前置约束：异常处理函数内禁止堆分配（可能与正在分配的上下文互相破坏）
  ├─ 过滤：ExceptionCode == EXCEPTION_SINGLE_STEP && (Dr6 & 0xF) > 0
  ├─ 逐个 Dr6 触发位检查（最多 4 个槽位）：
  │    HitCount > 0 → 递减；减到 0 → Status = Remove_ReachedHitCount, bTriggered = true
  │    HitCount == 0（-1，always）→ bTriggered = true
  │    记录 Breakpoint.Context = 当前 asCContext（判断是脚本还是 C++ 写入）
  ├─ ApplyBreakpointsToThreadContext(当前异常上下文)   就地重写 Dr 寄存器（处理 Remove 状态的槽）
  ├─ Dr6 = 0                                           清触发标志，否则一次中断会多次触发
  ├─ bCppBreakpoint 且 VS 调试器在场 → UE_DEBUG_BREAK()  真正断进 C++ 调试器
  └─ return EXCEPTION_CONTINUE_EXECUTION               吞掉异常继续执行
```

**关键的延迟停顿设计**：SEH 处理函数里不能安全做堆分配（FString、发消息都要堆），所以**硬件断点命中本身不停**，只置 `bBreakNextScriptLine = true`，真正的停顿发生在**下一行脚本字节码的 LineCallback**（`ProcessScriptLine` [A] 段）里——那里可以安全分配内存、发消息。若写入发生在纯 C++（没有活跃脚本上下文），则脚本下次进入调试器管控时才停。

`ClearAllAngelscriptDataBreakpointsFromHandler()` 是给"数据断点刷屏把编辑器卡死"准备的逃生舱：从 VS 即时窗口调用，让 SEH 处理器在下次触发时清掉全部数据断点。

### 7.3 作用域失效（StackPopCallback）

变量地址在 AngelScript 栈上时，栈帧弹出即失效。`ProcessScriptStackPop`（`:527-543`）在每次栈帧弹出回调中检查所有数据断点地址是否落在 `[OldStackFrameEnd, OldStackFrameStart]` 区间内（栈向下生长，start 是高地址）：

```
命中 → Status = Remove_OutOfScope, bTriggered = true, bBreakNextScriptLine = true
```

下一行 LineCallback 时以 "Variable Out Of Scope" 的信息暂停，随后通过 `ClearDataBreakpoints` 消息通知 DAP 端同步删除断点 UI。

### 7.4 触发后的报告（ProcessScriptLine [A]）

下一行脚本执行时统一结算所有 `bTriggered` 的数据断点：

- `Keep` → "Data breakpoint (name) triggered!"（`Context == nullptr` 时附加 "in C++!"）
- `Remove_ReachedHitCount` → "…(HitCount reached, Data Breakpoint disabled!)"
- `Remove_OutOfScope` → "Variable Out Of Scope, Data Breakpoint disabled!"
- 每条各发一次 `HasStopped`（reason = exception，DAP 端当异常暂停显示）；`Status != Keep` 的从表中移除并回推 `ClearDataBreakpoints(ids)`，再 `UpdateDataBreakpoints()` 重写 Dr 寄存器。

## 8. 连接与状态生命周期

```
                 StartDebugging              StopDebugging / last debug client disconnects
   (idle) ───────────────────────► (debugging) ─────────────────────────────────► (idle)
                                    bIsDebugging = true      bIsDebugging = false
                                    ClearAllBreakpoints()    bIsPaused = false
                                    (fresh state per session) ClearAllBreakpoints()
                                                               UpdateLineCallbackState()
        ▲   LineCallback / Exception                   Continue / Step / StopPIE
        └────────────► (paused) ◄──────────────────────────────
                          bIsPaused = true                 bIsPaused = false
                          game thread spins in            bBreakNextScriptLine = false
                          PauseExecution()                 condition frame cleared
```

- **按客户端记账**：`ClientsThatAreDebugging` / `ClientsThatWantDebugDatabase` 分开维护；最后一个调试客户端掉线（连接断开、PingAlive 超时判定）时自动结束调试态并清断点（`ProcessMessages` 的清理逻辑，`:614-639`）。
- **PingAlive**：调试中每 5 秒向调试客户端发心跳；发送队列里消息 10 秒仍发不出去也判掉线。
- `StopPIE`：结束 PIE 并复位暂停/单步状态——防止"停在断点上时退出 PIE"卡死在忙等里。
- `EngineBreak`：暂停中收到该消息则 `UE_DEBUG_BREAK()` 附加原生调试器（适配器中已注释掉调用）。

## 9. 值得注意的设计总结

| 设计 | 动机 |
|---|---|
| 三层门控（全局 CanEver / Always + 模块 hasBreakPoints） | 行回调逐行调用太贵，非调试态必须接近零开销 |
| 忙等式暂停（游戏线程自旋） | 暂停时栈/上下文完整可用，变量求值零快照成本；代价是暂停期间编辑器整体冻结 |
| 断点行"向前吸附"（FindNextLineWithCode） | 行号必须对齐真实字节码，回告漂移让 UI 显示准确位置 |
| IgnoreBreakLine/Section 去抖 | 一行字节码会多次回调（循环/多语句），避免同位置连环停 |
| 单步 = 标志 + 帧条件豁免 | 不依赖虚拟机的 step 指令，纯外挂逻辑即可实现三种 step |
| 硬件断点延迟到下一行停顿 | SEH 处理器里禁止堆分配，把有堆依赖的报告/暂停逻辑挪回安全的 LineCallback |
| 暂停时重置 `m_loopDetectionTimer` | 编辑器的"脚本死循环超时"检查不能把断点停留误判为死循环 |
| 数据断点栈出栈失效检测 | 栈上变量地址被复用前必须摘除断点，否则会在无关变量写入时误触发 |
